# Word协议表格信息智能提取与匹配系统 - 项目总结报告

---

## 一、调研情况（项目背景与技术选型调研）

### 1.1 项目背景

在通信协议研发与测试过程中，大量协议文档以 Word(.doc/.docx) 格式编写，其中包含数十甚至上百张表格，涵盖字段定义、端口分配、消息ID映射、bit位定义等多种类型。传统的人工方式需要逐表逐行转录到 Excel，耗时且易出错。

本项目的核心目标是：**自动化识别协议 Word 文档中的各类表格，智能提取结构化信息，并按照标准模板生成规范化 Excel 输出**，将人工数小时的工作缩短至分钟级。

### 1.2 语义匹配技术调研

字段映射是系统的核心难点——不同供应商的协议文档对同一字段命名各异（如"参数名称"/"字段名"/"变量名"），需要智能匹配到标准目标字段。

#### 1.2.1 BGE 嵌入模型调研

项目初期对语义匹配技术进行了系统性调研，关注了以下轻量级嵌入模型：

| 模型 | 特点 | 评估 |
|------|------|------|
| **Sentence-BERT (sBERT)** | 基于 BERT 轻量化改造，专为短文本语义向量生成设计；推理速度比标准 BERT 快约 10 倍；支持中文预训练权重 | 适合短文本语义匹配，中文支持良好 |
| **BGE (BAAI General Embedding)** | 智源研究院推出的通用嵌入模型，在 MTEB 中文榜单表现优异；支持多种尺寸（small/base/large） | 中文语义理解能力强，但模型较大 |
| **ERNIE 3.0 Tiny / Nano** | 百度出品的中文领域优化模型；对"中文术语缩略/同义词"捕捉能力强；Nano 版本模型体积约 100MB，支持 CPU 推理，单条匹配耗时 < 10ms | 中文领域表现优异，轻量化适合本地部署 |

#### 1.2.2 最终方案：ERNIE 3.0 Nano + 多级匹配降级策略

经调研后选择 **PaddlePaddle ERNIE 3.0 Nano** 作为语义匹配引擎，核心理由：

- **中文语义理解优秀**：对"形号→型号"等常见笔误有较高容错
- **轻量化部署**：模型约 500MB，CPU 推理即可，无需 GPU
- **模型与程序分离**：模型文件独立存放，不打包进 exe

匹配逻辑设计为三层优先级降级策略：

```
字段输入
    ↓
第一层：精确匹配（知识库中完全一致的映射，confidence ≥ 0.9）
    ↓ 未命中
第二层：别名匹配（预设的字段别名映射表，confidence = 0.85~0.95）
    ↓ 未命中
第三层：模糊匹配（基于 difflib.SequenceMatcher 的字符串相似度，threshold = 0.7）
    ↓ 未命中
第四层：语义匹配（ERNIE 3.0 Nano 向量余弦相似度，threshold = 0.8，当前已禁用）
    ↓ 均未命中
标记为 unmatched，提供前5个最相似候选供人工选择
```

> **当前状态**：语义匹配层（ERNIE 3.0 Nano）的代码已完整实现于 `backend/services/embedding_service.py`，支持自动加载模型、文本向量化和余弦相似度计算。但为避免部署环境缺少 PaddlePaddle 依赖导致启动失败，当前版本已将语义匹配注释禁用，降级为基于 `difflib.SequenceMatcher` 的纯字符串模糊匹配。需要时可取消注释重新启用。

### 1.3 文档解析技术调研

#### 1.3.1 Word 文档解析方案对比

| 方案 | 优势 | 劣势 | 决策 |
|------|------|------|------|
| **docx2python** | 提取速度快，输出结构简单 | 新版本 API 变更（`doc.body` 替代 `text_runs`），对合并单元格处理不精确 | 保留依赖但不再作为主解析方案 |
| **python-docx + 虚拟网格算法** | 精确还原合并单元格（gridSpan/vMerge），可访问底层 XML | 开发复杂度高，需自行处理行列对齐 | **最终选用** |

#### 1.3.2 最终解析方案

选用 **python-docx** 直接操作 Word 文档的 XML 结构，自研虚拟网格算法：

- **网格构建**（`_build_grid`）：遍历 `w:tc` 元素，处理 `gridSpan`（水平合并）和 `vMerge`（垂直合并），将表格转换为规整的二维文本网格
- **表头去重**（`_dedup_headers`）：水平合并产生的相邻重复列自动合并，空表头替换为 `column_N`
- **信息名称提取**（`_extract_msg_name_from_info_row`）：从"信息名称行"中过滤固定噪声词，提取有效消息名

### 1.4 知识库存储方案调研

| 方案 | 优势 | 劣势 | 决策 |
|------|------|------|------|
| **MySQL** | 结构化查询，支持并发 | 部署复杂，需安装数据库服务 | 初期设计 |
| **JSON 本地文件** | 零部署依赖，exe 打包友好，可读性高 | 不支持并发写入 | **最终选用** |

> 详见内存 `知识库系统从数据库迁移至本地JSON文件`。

### 2.3 表格识别类型体系

| 表格类型 | 识别特征 | 处理方式 |
|----------|----------|----------|
| **field_def** (字段定义表) | 含"数据类型/内容/序号"等列名 | 核心输出表，经清洗后写入Excel |
| **port_allocation** (端口分配表) | 含"信源系统码+信宿系统码+信息内容" | 构建全局端口字典，注入字段定义表 meta |
| **message_id** (消息ID表) | 含"消息ID+信息内容"，≤7列 | 构建消息ID字典，注入字段定义表 meta |
| **bit_def** (位定义表) | 含"位号+状态参数" | 当字段的"数据类型"列含"见表"字样时，将bit行作为子行附加 |
| **skip** (干扰表) | 前置段落含"干扰表格/测试用"，或表头含"测试指令/周期"，或帧格式表 | 跳过不处理 |

### 2.4 字段定义表的三种结构类型

| 类型 | 特征 | 表头位置 |
|------|------|----------|
| **A型（含信息名称行）** | 行0含"信息名称/通信帧名称" | 行1~7中搜索含"数据类型"等关键字的行 |
| **B型（行0即列名）** | 行0直接含"数据类型/内容"等列名 | 行0 |
| **C型（聚合式）** | 前置段落含"聚合式"，元数据横向排列 | 行0~7中的多行元数据 + 后续表头行 |

### 2.5 颜色标记规则（Excel导出）

| 颜色 | 含义 | 触发条件 |
|------|------|----------|
| 🔴 **红色** | 推断/不确定值 | 类型从"字节"推断为UINT8、单位从备注中提取、值域来自备注提取、嵌套表引用 |
| 🔵 **蓝色** | 辅助表关联补充 | 从端口分配表/消息ID表注入的元数据（信源系统码、消息ID等） |
| ⚫ **黑色** | 原始字段直接映射 | 直接来自原始文档的字段值 |

### 3.3 核心模块详解

#### 3.3.1 表格检测解析（table_detector.py）

核心类：`TableDetector`、`DocumentParser`

**关键技术**：
- **虚拟网格算法**（`_build_grid`）：遍历 Word XML 的 `w:tc` 元素，处理 `gridSpan`（水平合并填充）和 `vMerge`（垂直合并继承），将任意复杂度的合并单元格表格精确还原为规整的二维文本网格
- **表格类型自动识别**：按优先级依次匹配端口分配表 → 消息ID表 → bit位定义表 → 字段定义表（A/B/C三种结构）
- **干扰表格过滤**：6种过滤规则（干扰前置段落、干扰表头关键词、帧格式表、示例表、无数据类型关键字、无有效数据行）
- **上标/下标处理**：识别 `w:vertAlign` 属性，将上标文本自动添加 `^` 前缀，下标添加 `_` 前缀

#### 3.3.2 表格关联处理（table_linker.py）

核心类：`TableLinker`

**关键功能**：
- **全局字典构建**：扫描所有表格，建立端口字典（消息名→{信源系统码,信源机器码,...}）和消息ID字典（消息名→消息ID）
- **bit子行附加**：检测字段行的"数据类型"或"备注"列是否含"见表"字样，自动定位对应 bit 定义表，为每个 bit 位生成子行（含位号、状态参数、推断数据类型）

#### 3.3.3 数据清洗处理（data_cleaner.py）

核心类：`DataTypeConverter`、`RangeValueFormatter`、`FormulaStandardizer`、`UnitExtractor`、`DataProcessor`

**关键功能**：
- **类型标准化**：70+ 种原始类型表述映射到标准类型（UINT8/16/32/64、INT8/16/32、FLOAT/DOUBLE/ENUM），支持中文别名和拼写错误容错
- **值域格式化**：统一 `[min, max]` 方括号格式，支持十六进制保持原样，负数保护（防误判为分隔符）
- **公式标准化**：中文描述（"乘以10"、"除以100"）→ 代数表达式（`10x+0`、`0.01x+0`），支持复杂表达式（`(X/4096)×21` → `0.00512695x+0`）
- **备注智能分类**：从备注中自动识别并提取值域、单位、转换公式，保留原始备注内容不变

#### 3.3.4 字段智能匹配（field_matcher.py）

核心类：`EnhancedFieldMatcher`

**匹配策略**：
1. 精确匹配：知识库中 `source==field && confidence≥0.9`
2. 别名匹配：预设映射表（"参数名称"→"参数"、"时间"→"时间戳"）及模糊别名（相似度>0.8）
3. 模糊匹配：`SequenceMatcher` 计算字符串相似度（阈值0.7）
4. 语义匹配：ERNIE 3.0 Nano 余弦相似度（阈值0.8，当前已禁用）
5. 未匹配：返回 Top-5 最相似候选

#### 3.3.5 Excel 导出（excel_exporter.py）

核心类：`ExcelExporter`

**关键设计**：
- **模板驱动**：基于 `协议模板.xlsx` 复制后填充，确保输出格式一致
- **主行/子行架构**：首行写完整元数据（名称、ID、信源信宿等），后续行只写字段内容
- **三色标记体系**：黑色（原始值）、红色（推断值）、蓝色（关联补充）
- **文件自动删除**：下载后自动清理服务端文件，确保结果只保留一份

### 4.2 部署方式

#### 方式一：开发模式

```bash
# 后端
cd backend
pip install -r requirements.txt
python app.py                    # 启动在 http://localhost:5001

# 前端
cd public
npm install
npm run dev                      # 启动在 http://localhost:5173
```

```bash
# 使用 PyInstaller 打包为单个 exe
build_exe.bat                    # 或 pyinstaller build.spec

# 打包后结构
dist/
├── protocol-tool.exe            # 可执行文件
├── models/
│   └── ernie-3.0-nano-zh/      # 语义模型（独立存放）
├── word/csvfile/协议模板.xlsx   # Excel 模板
└── backend/                     # 动态生成的数据目录
```

#### 方式三：生产环境部署

```
Nginx 反向代理
├── /              → 前端 dist/ 静态文件
├── /api/*         → Gunicorn/UWSGI (127.0.0.1:5001)
└── /health        → 健康检查端点
```

### 4.3 启动脚本

| 脚本 | 功能 |
|------|------|
| `启动工具.bat` | 一键启动前后端 |
| `build_exe.bat` | PyInstaller 打包 |
| `deploy.bat` | 生产部署脚本 |
| `install_paddle.bat` | 安装 PaddlePaddle 模型依赖 |

### 4.4 健康检查

```bash
GET http://localhost:5001/health
# Response: { "status": "healthy", "version": "2.0.0" }
```

### 4.5 注意事项

1. **Flask debug=False**：Windows PowerShell 中 debug=True 会导致启动失败
2. **中文路径兼容**：打包后的 exe 支持中文路径，但 Python 命令执行时需注意编码
3. **文件自动清理**：下载后自动删除服务端临时文件，结果仅保留最近一份
4. **任务持久化**：最近 50 条任务记录持久化到 `tasks_history.json`，重启后可恢复
