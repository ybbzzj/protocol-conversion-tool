# 后端解析流程重构说明

> 重构时间：2026-02-27  
> 分支：test-yyq

---

## 一、背景

原有实现使用 `docx2python` 进行表格解析。该库会**自动填充合并单元格**（水平合并和垂直合并），导致：

1. 无法区分"真实数据"与"被填充的占位值"，引发列数与表头不匹配
2. 垂直合并（跨行合并）续行内容被重复计入数据行
3. 信息名称行（行0）的消息名被误识别为多个重复行

本次重构将 **`docx2python` 完整替换为 `python-docx`**，通过直接读取 OOXML 中的 `w:gridSpan`（水平合并）和 `w:vMerge`（垂直合并）属性，精确构建表格网格。

## 三、各文件详细改动

### 3.1 `table_detector.py`

#### 核心原理变化

```
旧：docx2python → 自动填充合并单元格 → 无法区分真实/填充值
新：python-docx → _build_grid() → 精确处理 gridSpan/vMerge
```

#### 新增函数

| 函数 | 作用 |
|------|------|
| `_build_grid(table)` | 构建精确的文本网格，返回 `grid[r][c]` 和 `is_vmerge_cont[r][c]` |
| `_dedup_headers(header_row)` | 对表头行去重（水平合并产生的重复列只保留第一个） |
| `_extract_msg_name_from_info_row(row_unique)` | 从信息名称行（行0）提取消息名，过滤噪声词 |
| `_extract_name_from_para(para_text)` | 从前置段落文本中提取表格标题 |
| `_is_noise_table(grid, preceding_para)` | 判断是否为干扰/无效表格 |
| `_parse_aggregate_meta(text)` | 解析聚合式元数据（如 `BC→RT1-SA0-模式码0x03`） |

#### 支持的三种表格结构

| 类型 | 特征 | 示例 |
|------|------|------|
| **A型**（信息名称行） | 行0含"信息名称"/"通信帧名称"，消息名在同行 | 大多数协议参数表 |
| **B型**（前置段落标题） | 行0直接是列名，前置段落含表格名 | 部分状态信息表 |
| **C型**（聚合式） | 行0含信息名称，行1~N为元数据区，再往后才是列名行 | 信息流表征示意 |

#### 表格类型字段 `table_type`

每个解析后的表格字典新增 `table_type` 字段：

| 值 | 含义 |
|----|------|
| `field_def` | 字段定义表（协议参数表），需要输出到 Excel |
| `port_allocation` | 端口分配表，仅用于关联 |
| `message_id` | 消息ID映射表，仅用于关联 |
| `bit_def` | bit 位定义表，用于生成子行 |
| `skip` | 干扰/无效表格，直接跳过 |

### 3.2 `table_linker.py`

#### 核心逻辑变化

旧版依赖"邻近关联"（前后5个表格内查找），容易漏配；  
新版构建**全局字典**，精确查找，不受表格位置影响。

#### 新增方法

| 方法 | 作用 |
|------|------|
| `_build_port_dict(tables)` | 扫描所有端口分配表，建立 `消息名→{信源系统码, 信宿系统码...}` 字典 |
| `_build_msgid_dict(tables)` | 扫描所有消息ID表，建立 `消息名→消息ID` 字典 |
| `_build_bit_def_map(tables)` | 收集所有 bit 位定义表 |
| `_attach_bit_rows(field_row, bit_tables, t_idx)` | 检查字段行是否引用了 bit 位表，如有则生成子行列表 |
| `_lookup_in_dict(msg_name, d)` | 支持精确+部分子串匹配的字典查找 |

#### `link_tables()` 新流程

```
1. 构建全局 port_dict、msgid_dict
2. 收集所有 bit_def 表
3. 对每个 field_def 表：
   a. 通过 _lookup_in_dict 注入端口信息到 meta
   b. 通过 _lookup_in_dict 注入消息ID到 meta
   c. 对每个字段行，调用 _attach_bit_rows 检查是否需要插入 bit 子行
4. 只返回 field_def 类型的表格（辅助表消化后不再输出）
```

#### bit 子行格式

```python
{
    '_is_bit_row': True,
    '子内容': '状态参数名称',
    '类型（bit）': 4,           # 位数（如 D6~D3 → 4位）
    '_bit_str': 'D6~D3',
}
```

### 3.3 `data_cleaner.py`

#### 新增类

**`RangeValueFormatter`** - 值域/取值范围格式标准化

目标格式：`0~4294967295`（十进制，`~` 分隔）

| 输入 | 输出 |
|------|------|
| `0x00~0xFF` | `0~255` |
| `[0, 255]` | `0~255` |
| `0-400` | `0~400` |
| `{0,1,2,3}` | `0~1~2~3` |

**`FormulaStandardizer`** - 数据处理公式标准化

| 输入 | 输出 |
|------|------|
| `乘以10` | `10x` |
| `除以100` | `x/100` |
| `×0.125` | `0.125x` |
| `量化单位0.5°` | `0.5x` |

#### `DataTypeConverter` 扩充映射

新增以下类型别名（原版缺失）：

```python
'16位无符号整型' → ('UINT16', 16)
'32位无符号整型' → ('UINT32', 32)
'单精度浮点'     → ('FLOAT32', 32)
'双精度浮点'     → ('FLOAT64', 64)
'LONG'          → ('UINT32', 32)
'ENUM'          → ('ENUM', 0)
```

#### `DataProcessor.process_row()` 新增 `formatted` 输出

```python
result = {
    'cleaned':   {...},   # 原始字段清洗
    'converted': {...},   # 类型转换（标准类型、位数）
    'formatted': {        # 新增：格式化结果
        '值域': '0~255',
        '转换公式': '10x',
    }
}
```

### 3.4 `excel_exporter.py`

#### 主/子行架构

| 行类型 | 名称列 | 内容列 | 元数据列 |
|--------|--------|--------|----------|
| **主行**（每个消息第一行） | 填消息名称 | 填第一个字段 | 填信源/信宿/ID等 |
| **普通子行** | 空 | 填字段内容 | 空 |
| **bit 子行** | 空 | 填 bit 状态名 | 只填类型（bit）列 |

#### 颜色规则

| 颜色 | 触发条件 |
|------|---------|
| 🔴 红色（`#FF0000`） | 判读公式/单位是从备注等其他字段提取的，不确定准确性 |
| 🔵 蓝色（`#0070C0`） | 来自辅助表关联补充的元数据（端口/ID表） |
| ⚫ 默认 | 直接从原始字段映射，准确可信 |

> 注：蓝色标注当前仅在字段级声明，实际写入 Excel 时已支持，后续可按需开启。

#### `META_TO_EXCEL` 映射表

```python
META_TO_EXCEL = {
    '消息ID':     'ID',
    '信息标识':   'ID',
    '信息ID':     'ID',
    '信源系统码': '信源系统码',
    '信源机器码': '信源机器码',
    '信宿系统码': '信宿系统码',
    '信宿机器码': '信宿机器码',
    '子地址':     '子地址',
}
```

追加到备注的元数据键：`传输周期`、`发起时机`、`错误处理`、`其他`
