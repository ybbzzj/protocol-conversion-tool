## 先说整体：一条流水线分两段

不管之前还是现在，程序处理每张表都是**两段式**：

- **第一段「识别」**：`_parse_single_table` 当总调度，`_is_noise_table` 拍板——"这到底是不是一张协议表？"（噪音关）
- **第二段「抽表头」**：`_parse_field_def_table` 拍板——"表头在哪一Row？字段怎么抽？"

你这次所有改动都砸在**第二段**，第一段只动了"识别混合表的那把钥匙词"。

## 一、之前的流程（bzj-logging-0627）

### 第一段·识别（`_is_noise_table`）
顺序：示例表→配置匹配→智能识别（端口/ID/bit）→噪音过滤→逃生（目标消息名）。
噪音过滤内部：段落干扰词/帧格式→丢；端口表、消息ID表→留；**配置兜底**（row0 跟配置字段重合 ≥3列 或 ≥50%）→留；表头干扰词 / 整表找不到数据类型字→丢。

### 第二段·抽表头（`_parse_field_def_table`）
这是关键，之前长这样：

1. **先判断 row0 含不含 `'信息名称'` 或 `'通信帧名称'`**（这两个词是**硬编码写死**的）
   - 含 → 进 **Type A** 分支：从行1向下扫到第7行，靠"数据类型/内容+序号"这些关键词找真表头；元数据行靠"含元数据词 且 没内容没序号"来跳过；找到后上面的行抽进 `meta`（**空值也照写**）
   - **不含 → 进 B/C 分支：只看第 0 行！**
     - row0 里有 `数据类型/内容/参数…` → 表头=行0，往下抽
     - **row0 里没有这些词 → 整张表 `skip`，直接丢掉**

> 看出来了吧：之前对"行0 不是表头"的表，只有一条活路——首行得是那两个写死的"信息名称/通信帧名称"词，否则就当 B/C 死看 row0，看不着就整表报废。

## 二、现在的流程（fix/typea-noise-filter + 未提交改动）

第一段基本没变，只把"识别混合表的钥匙词"从写死改成**可配置**（`mixed_table_markers`，默认 `{信息名称, 通信帧名称, 通信帧名字, 信息标识, 上级信息名称}`）。

第二段彻底重写 B/C，Type A 也补了结构校验。核心思想变了：**不再靠"这行里有没有元数据关键词"来区分元数据/字段，而是看"这行下面有没有真实数据块"**。

1. 判断 row0 含不含 `mixed_table_markers`（可配，默认含"通信帧名字"）
   - 含 → **Type A**：向下扫 + **结构校验**（下方得有数据块）+ 表头上方行抽进 `meta`（空值跳过）
   - 不含 → **B/C 重写**：向下扫 0~7 行，每行做**结构校验**，多候选时**优先选含"字段词（序号/内容/类型）"的行**，表头上方所有行抽进 `meta`（绝不进字段）

## 三、逐条区别，用你那张「自检结果」表对上

你那张表长这样（之前一直没输出）：
```
行0  通信帧名字 | 自检结果 | 信息流向      ← 元数据(首行)
行1  前置条件    | 非周期   | 发送周期或次数 ← 元数据
行2  错误处理    | …                         ← 元数据
行3  序号 | 内容 | 长度 | 值域 | 单位 | 说明 ← 真表头
行4+ 温度/湿度…                           ← 真实数据
```

**区别①：混合表钥匙词从"写死"变"可配 + 默认含通信帧名字"**
- 之前：只认 `通信帧名称`。你的表写的是「**通信帧名字**」（带"字"），差一个字→不进 Type A→走 B/C→只看行0（行0是"通信帧名字/自检结果/信息流向"，没有"数据类型/内容"）→**整表 skip**。这正是你"配了序号/内容/长度/值域还是没输出"的真根因。
- 现在：`mixed_table_markers` 默认就含「通信帧名字」→进 Type A→向下扫到行3真表头。

**区别②：B/C 不再死看第 0 行（结构判断兜底）**
- 之前：B/C 分支 `if has_type or has_content: 表头=行0; else: return skip_result`——一行定生死。
- 现在：B/C 也向下扫 0~7 行，每行用新加的 `_record_rows_below()` 查"你下面有没有真实记录块"。这样**就算首行识别混合表失败，只要下方真有字段数据块，也能兜住**。

**区别③：元数据只进 `meta`，不进字段输出，且空值跳过**
- 之前：横向提取元数据时空值也写，于是 `meta` 里会出现 `发送周期: ''` 这种噪音。
- 现在：新加 `_extract_meta_row()`，**空值直接跳过**；表头之上所有行统一进 `meta`，**绝不会混进 `data_rows`（字段行）**。你这张表最终：字段行只有行3+的数据，干净；`前置条件=非周期` 老老实实待在 `meta`。

**区别④：多候选时优先选"字段词"行（解决"元数据和字段长得像"）**
- 这是你最担心的一点。现在收集所有"像表头"的候选后，排序优先看 `has_field_kw`（含 序号/内容/类型），其次看下方数据块多少。**哪怕某行元数据长得跟字段一模一样（比如写了信源/信宿/周期），只要它下方没数据块、又不是含字段词的那行，就不会被误当表头。** 破局点就是"看结构，不看词"。

**区别⑤：CRC 那条——现在跟之前一样，不再是区别**
- 之前基线就是"末行含 CRC 就删最后一行"。我上一轮顺手加的"让带属性的 CRC 保留"已经按你要求回退了，所以现在 = 基线原样。

**区别⑥：修了个上一轮埋的潜伏 bug**
- 上一轮给混合表识别加 `self.mixed_table_markers` 时，在模块级函数 `_is_noise_table`（它没有 `self`）里误用了 `self.mixed_table_markers`。当时单测只跑 `_parse_field_def_table` 没暴露，这次跑你真实 docx 才崩。现已改成传参 `mixed_markers` + 模块级 `DEFAULT_MIXED_MARKERS`。

## 一句话总结区别

| 维度 | 之前 | 现在 |
|---|---|---|
| 混合表识别词 | 写死 `信息名称/通信帧名称` | 可配 `mixed_table_markers`，默认含"通信帧名字" |
| B/C 表头查找 | 只看第 0 行，看不着就丢 | 向下扫 0~7 行 + 结构校验 |

| 多候选表头 | 第一个像的就认 | 优先选含"字段词"的行 |
| 元数据落点 | 进 `meta`，空值也写 | 只进 `meta`，空值跳过，绝不进字段 |
| CRC | 见就删末行 | 同上（回退后无区别） |
